# Vue3 Laravel Admin 定制开发

把使用者描述的业务做成可用功能，保持基座的布局、权限和数据边界。此 skill 可随仓库使用，也可独立安装；所有必要约束在本目录内，不依赖维护者的内部记录或其他 skill。

## 先确定地基

- 当前目录已有本项目或派生项目时直接继续，检查 Git 状态、根 package.json、upstream.json、backend/app/Modules 与 frontend/src/components。以当前检出的实现和用户已有修改为准，不重新克隆或自动拉取覆盖定制。
- 没有项目、用户希望搭建后台时，优先使用 `https://github.com/DarkWinoom/vue3-laravel-admin.git`，在确定的空目标目录克隆；未指定版本时使用默认分支并记录实际 commit。不要从裸 Vue/Laravel 或另一套管理模板重新起步。
- 当前目录属于无关项目时，在独立目标目录建立基座；保留用户明确指定的框架/仓库，范围冲突时先澄清。
- 只安装 skill 不会创建后台。克隆、准备环境和部署步骤见 [启动与验证](references/setup-and-checks.md)。安装位置与业务项目是两个目录，进入业务项目后再执行命令。无法联网时可使用用户提供的完整本地基座，不能伪称已获取远程代码。

## 把需求做完整

1. 从需求确定页面用途、数据字段、操作权限和可验收行为。只有会影响实现的缺失信息才需要询问；其余使用现有页面的合理默认值。
2. 先找最接近的现有组件。改页面读 [界面与导航](references/frontend.md)；涉及数据、权限或 API 再读 [后端与契约](references/backend.md)。跨层功能两份都读。涉及桌面、CI、派生项目初始化或发布时另读 [桌面与发布](references/desktop-and-release.md)。
3. 简述组件及模块职责，完成与本次需求相关的页面、API、迁移、菜单、权限和契约连接。外观调整不引入数据库改造；新增真实业务不以模拟接口代替交付。
4. 运行与改动相关的检查，修复后复测。涉及登录/写入/权限时验证拒绝路径；界面变化验证操作、窄屏与明暗主题。检查矩阵见 [启动与验证](references/setup-and-checks.md)。
5. 告诉使用者新增了什么、从哪里进入、怎样验收和检查结果。沿用仓库与用户的提交约定；推送、公开发布和部署到他人环境须有相应授权。新业务不会自动推回基座仓库。

## 保持这些项目边界

- 基座是 Vue 3 + TypeScript + Naive UI + UnoCSS/SCSS，Laravel + MySQL 模块化单体。保留双 pnpm workspace、锁文件及上游许可证；只为需求所需能力增加依赖。
- 默认中文，复用官方 Soybean 风格与现有组件；不添加语言切换或第二套 UI。尊重使用者明确要求的后续产品变化。
- 路由页负责组合，业务状态在 composable，表单用明确的 props/emits。Vue 样式使用 `lang="scss"`；不改变现有 profile 外观。可见文字至少 14px，字体和图标不回退到运行时 CDN。
- 默认两层菜单。前端隐藏按钮不是授权；每个 API 必须验证当前身份与权限。保持个人中心、首页、登录和错误路由的既有生命周期。
- 访问/刷新令牌保持当前会话设计；不写入 localStorage。保留刷新单飞、跨账户旧请求隔离与路由 registry，不用一次性缓存的权限替代后端检查。
- 角色、权限、用户授权通过 Access 应用入口和事件投影变更。普通业务使用自己的应用命令、查询和事务，不把所有业务强制做成事件溯源。
- 根 env 区分开发/测试/生产；`VITE_*` 会进入客户端。测试仅使用独立测试库，迁移保留用户已有数据。新增写操作的审计与业务同事务，只记录必要、已脱敏字段。
- 文档与代码一起维护：面向使用者的入口是 README.md，技术细节在 README.development.md，本 skill 的规则/路径也要随实现同步。更新 skill 本身不等于升级业务基座。

具体命名、版本和路径若与未来检出版本不同，先核对当前源代码再调整，不机械套用旧清单。不要把桌面发布、CI 或生产部署当作普通界面定制的默认附加任务。
